# Archived Flash artifacts: verified formats and current limits

This note separates **Java applet classes**, **Flash content**, and **native Flash players**. It records both static inspection and a small, independently JDK-compared **execution of original Java Flash class methods**. The *full* Flash Applet was not run, rendered, or converted to a working player; native Adobe/Chromium binaries were not launched. Magnolia's `.class`/JAR adapter remains a bounded JVM subset; see [applet.md](applet.md).

## A genuine historical Java Flash player: acquired and inspected

Macromedia's [Flash 5 Players readme](https://stratagem.pangaea.de/plugin/ReadMe.html) expressly describes **Flash Player Java Edition**, its `FlashSmall` and `FlashApi` folders, and `FlashApi.zip`. **It plays Flash 2 features only**; the readme says it does *not* support Flash 3, 4 or 5 files/features. This is a distinct historical Java player, not the native Adobe/Chromium PPAPI plugin or later Adobe projector. The [Flash Player SDK readme](https://github.com/macromedia-os/Macromedia-Flash-SDK/blob/main/Readme.html) says the Java sample includes the *complete set of class files for the java player*.

A copy was obtained by cloning the [archived SDK repository](https://github.com/macromedia-os/Macromedia-Flash-SDK/tree/main/JavaFlash) at commit `bb8536a8f564510f979eb8e09924bc259651a0a9` (a third-party upload, **not** an independently verified official Macromedia checksum). In `JavaFlash/FlashApi.ZIP`: **85,800 bytes**, SHA-256 **`fbb2149179c1c5a32bd9aa7f479a1e760e36e18dbd8e48147729ca67822932c2`**. Its **20 `.class` files** total 82,856 uncompressed bytes, all matching the repository's expanded copies; ZIP timestamps are 1998-04-13. Every class begins `CA FE BA BE` and reports JVM **45.3**. `com/macromedia/flash/Flash.class` (9,636 bytes, SHA-256 **`74bea8580390e8488cce578ac0d09370c1e7cc73109817dd923b1e54551313bc`**) **extends `java.applet.Applet` and implements `Runnable`**; its `paint(Graphics)` and `start()` are actual Java methods. `FlashApi.class` (SHA-256 `da6ffbb273e156619f2093461485fb194d7aec9a6ed0a5552f591aa4e89894e1`) exposes Java playback API methods. These format findings use ZIP, class-file and `javap` static readers; **separate selected methods** of the genuine `Matrix`, `SParser` and `Rect` classes were later executed as documented below. The `Flash` Applet/player was not executed.

Magnolia recognizes the original upper-case `.ZIP` filename and **parses all 20 classes**. An earlier preflight stopped at `Flash.<init>()V` byte 98 (`dconst_1`). The patch author reports that a bounded F/D implementation now decodes that constructor, and that a fresh **selected-entry** `run --class com/macromedia/flash/Flash` stops *before execution* at **`Flash.start()V at byte 6: unsupported JVM opcode 0xc2`** (`monitorenter`); those runs were **not reproduced in this tree** (no JDK available; the post-port tree has not been built or executed). A real monitor/thread scheduler, not an ignored no-op, is required; the whole player is **not** runnable. This is **not** a working Oak conversion. Static `javap` inventory finds approximately 19,245 JVM instruction listings across the 20 classes, including doubles/longs, `ldc2_w`, 17 methods with exception tables, `jsr`/`ret`, monitors, switch instructions and interface calls. Referenced JDK classes include AWT graphics/imaging, audio, `Thread`, URL and I/O. Complete verified JVM primitive/exception/monitor/thread and AWT/image/audio/browser support would be needed before this archive could run, then SWF 2 playback would still need content/host tests. **Finding these classes neither enables modern Flash games nor proves that Rapper Rhythm uses them.**

The `build coverage --entry /path/to/FlashApi.ZIP --json` **whole-input** inventory (same archive hash above) now reports **277 methods, 321 fields, 199 decoded bodies and 122 blockers**. Its earlier identity-branch state was 173/277 and 175 blockers (initial baseline 166/182). Modeling `java.awt.Point` admitted 22 more bodies (195/277, 126 blockers); exact, budgeted `System.arraycopy` then admitted four more (199/277, 122 blockers). Two formerly blocked original bodies now decode, while two others advance to `ColorModel` signature blockers. **These arraycopy-dependent original methods were not executed against a reference JVM.** At the author-reported 219/100 checkpoint the remaining first-blocker categories include missing signature/supertype references, 17 exception-table methods, AWT imaging (`Image`, `ColorModel`, consumers/producers), stateful I/O, threads, `sun/audio/AudioPlayer` and unmodeled Java API calls; at the 199/122 checkpoint recorded in this tree they also included 14 first-blocked `i2l` sites. Exact `Point.x`/`y` field reads/writes, constructors and a few mutable helpers now execute in both new fixtures and **selected original `Rect` bytecode**; this is not a complete AWT toolkit. `wide` category-one locals/`iinc`, switches, primitive char/short arrays, category-one stack shuffles and reference identity branches are likewise bounded, but none implements the monitor/thread/AWT/stream host contract or the wider two-slot numeric and library gaps (the constructor's `dconst_1` block is author-reported as now decoded; not reproduced here). The report can include a signature blocker and a bytecode blocker for one member, but stops decoding each body at its first failure; these counts are not a full runtime compatibility proof. A newer lineage additionally reports 218/277 Flash bodies and 101 first blockers after exact-limb long arithmetic, **219/277 decoded bodies with 100 first blockers after bounded `multianewarray`** (the newly decoded body is original `Bitmap.<clinit>`), and the patch author now reports a latest **221/277 with 91 first blockers** after bounded IEEE/exception/shuffle/stream work (an earlier checkpoint reported 96) — all unverified in this environment (no JDK). Some exception-table methods decode under the new bounded handler support; that does not guarantee their complete execution. The selected Flash Applet path is author-reported to stop at `monitorenter` (0xc2), not at `dconst_1`. See the [compatibility plan](applet.md).


### Original core bytecode actually executed, with a reference JVM oracle

[`tools/historical-core-matrix.sh`](../tools/historical-core-matrix.sh) verifies the original archive hash, extracts **unmodified** `Matrix.class` (SHA-256 `df934e7dce8756e79abe3360d1cea5a29818f4ed25f813ad0d1739abe8fca6c3`), `SParser.class` (`9fc21c5ec64e9daa32f163588f95d5ad18aae6cf1f73288c2932e11d882338db`) and `Rect.class` (`36e7b476cec00972cc31929a7dfb32d7ba5abb729e4356288dec8e7487110f74`), and compiles separate small Java *harness sources* against them. On JDK 11 with `-Xverify:all`, real `Matrix.<clinit>` and integer math produce `23, -2147483648, 2147483647, 11, 63, 0`; real `SParser` little-endian reads/cursor updates produce `33023, -1, -2147478988, 8`; real `Rect` containment/union/intersection with public `Point.x/y` produces 11 boolean lines. Native Magnolia executes those **same original method bytes**; standalone Oak, Builder JS/Node and generated Java match independent JDK outputs. Builder's self-contained **HTML** for both `SParser` and `Rect` runs their inline scripts in a network-free simulated DOM; this is not a real AWT window/event host. The generated Java emitter decodes modified-UTF-8 obfuscated identifiers into distinct `\uXXXX` Java escapes; that is not general non-ASCII `String` support in Oak/JS. Byte-exact original restoration is checked **separately** from execution.

One same-width Oak instruction edit in the original `SParser` unsigned read (`sipush 255` → `sipush 127`) produces a **new** `SParser.class`, checked by JDK `-Xverify:all`: the new bytecode and edited Oak both print `32895, -129, -2147478988, 8`. Independently, changing the original `Rect.Ɓ(Point)` minimum-x boundary branch from `if_icmpgt` to `if_icmpge` produces a **different JDK-verified `Rect.class`**. Two previously accepted boundary results become false in both edited Oak and its new class; Builder JS and generated Java also match. Each edited Oak separately restores **the original** class bytes, not the new ones. See [harness sources, exact outputs, Fliplay comparison and reproduction steps](../test/historical/README.md). The class methods exercised here are parser/math/Point geometry building blocks, **not** `Flash.<init>`, lifecycle, SWF decoding/rendering, sound, complete AWT or a converted working player. A fresh `build coverage --entry /path/to/FlashApi.ZIP --json` **whole-input** inventory after the bounded IEEE/exception/shuffle and reference/constructor/`StackMapTable` slices is author-reported to report **277 methods, 321 fields, 221 decoded bodies and 96 first blockers** (the preceding exact-limb-long checkpoint was 218/101; the width-aware checkpoint 199/120; the Point/arraycopy checkpoint 199/122), with the selected `Flash.start()` preflight still rejecting `monitorenter` — not reproduced here. This selected-path success cannot make the remaining whole-input blockers disappear.

The SDK repository's modern root `LICENSE` says MIT, but its historical `JavaFlash/Source/FlashApp.java` begins with a Macromedia proprietary/confidential notice. Do **not** assume that the uploader could relicense Macromedia binaries or redistribute/embed them in output. The SDK artifact remains outside the Magnolia repository; documentation records hashes and sources, not proprietary class files. You can reproduce the safe preflight on a lawfully obtained copy:

```sh
magnolia build inspect --entry /path/to/FlashApi.ZIP \
  --class com/macromedia/flash/Flash --check
# ... Unsupported: com/macromedia/flash/Flash.<init>()V at byte 98:
#     unsupported JVM opcode 0xf
# After a build with the bounded F/D support (author-reported, not run here):
magnolia build run --entry /path/to/FlashApi.ZIP \
  --class com/macromedia/flash/Flash
# ... [applet] com/macromedia/flash/Flash.start()V at byte 6:
#     unsupported JVM opcode 0xc2 (monitorenter); exit 1
```

## Rapper Rhythm ZIP: not acquired

The [Rapper Rhythm page](https://www.dedededrip.net/viewflash.php?id=rapperrhythm) advertises [`rapper_rhythm_executable.zip`](https://www.dedededrip.net/rapperrhythm/rapper_rhythm_executable.zip). On 2026-10-26 (America/Toronto; 2026-10-27 UTC), an unauthenticated request returned an HTML JavaScript-cookie challenge, **not ZIP data**. After the challenge, the same path with `?i=1` returned HTTP **404** and HTML, on both the `www` and bare-domain hosts. The [Wayback CDX index for this URL](https://web.archive.org/cdx/search/cdx?url=www.dedededrip.net%2Frapperrhythm%2Frapper_rhythm_executable.zip&output=json&filter=statuscode%3A200&collapse=digest) shows HTML responses rather than a captured ZIP. A link on the page is not proof that the current file exists.

**Consequently:** nothing is known from direct inspection about the ZIP's members or whether its EXE contains an Adobe Flash projector, embedded SWF, both, or something else. An uploaded copy or a demonstrably accessible binary mirror is needed. Do not replace it with a similarly named game from elsewhere and call it the same artifact. Do not execute an untrusted EXE to investigate it.

Both archived binaries were examined with `file`, checksum tools, PE/ELF metadata readers, and bounded byte/string inspection; neither was launched. An occurrence of `FWS`/`CWS` in an EXE is **not by itself** proof of a valid bundled SWF: player implementations contain format-related strings/data. The separately archived **player** EXE does not establish what the unavailable Rapper Rhythm game EXE contains.

[Flashpoint's extraction guide](https://flashpointarchive.org/datahub/Extracting_Flash_Games) describes a common *different* format: an EXE projector that packages a Flash player **with a particular SWF game**. The SWF is Flash content (ActionScript/AVM bytecode and assets), not a Java class or the Adobe player implementation. The `.fla` is an authoring project. Some third-party EXE wrappers instead depend on an external ActiveX player, so even an obtained EXE needs individual inspection. Chromium's [historical Pepper Flash packaging](https://github.com/adobe/chromium/blob/master/third_party/adobe/flash/flash_player.gyp) and [PPAPI interface documentation](https://chromium.googlesource.com/chromium/src.git/+/9.0.597.73/ppapi/documentation/index.dox) explain why the browser plugin is a distinct native component.

## Implications for Magnolia Builder / Oak

- Existing class/JAR → Oak/JS/HTML/Java paths accept supported **JVM bytecode**, magic `CA FE BA BE`. They cannot execute or translate a Windows PE projector, Linux ELF PPAPI plugin, or SWF just by changing a file extension. **Original-byte restoration** remains separate from **executing selected real methods** and from the tightly scoped **edited Oak → new `.class`/unsigned `.jar`** assembler (see [applet.md](applet.md)); none makes the *whole* Java Flash player executable yet.
- Running the native player *as itself* in self-contained Oak without a system JVM or external Flash runtime would require a verified **x86 machine-code execution/translation layer**, process memory and native OS ABI, plus either a PPAPI browser host (for the `.so`) or a Win32 GUI/audio host (for the `.exe`). Supporting arbitrary SWFs through that player additionally requires its actual Flash VM, renderer, I/O, timing, and security behaviors. This is an independent, substantial native-compatibility project, **not implemented** in the applet adapter. A SWF-only converter would be a separate Flash-content path, not conversion of the Adobe native player.
- For an **uploaded** game projector, first hash and inventory ZIP entries without launching programs; inspect PE headers/resources/overlays; validate any candidate embedded `FWS`/`CWS`/`ZWS` SWF against its declared length, compression, and tag structure; identify whether the player is included or external; report the Flash/ActionScript version. Do not promise runnable Oak/JS before interpreter and host parity tests exist.
- Archival download availability is not redistribution permission. Do not check proprietary Adobe player binaries into the repo or put them into generated self-contained output without resolving rights. Untrusted executables should be handled only by static inspection or in appropriately isolated environments.

**Current status:** selected unmodified Java Flash `Matrix`, `SParser` and Point-based `Rect` bytecode executes and matches a reference JVM across native Oak, standalone Oak, JS and generated Java; `SParser` and `Rect` also match as standalone inline HTML in an offline simulated DOM. The **full historical `Flash` Applet still fails selected execution preflight** at `Flash.start()V` `monitorenter` (0xc2) (author-reported; this tree not rebuilt) and has not played or rendered an SWF; Macromedia documents only Flash 2 features. The linked Rapper Rhythm ZIP remains inaccessible here (verified 404 after challenge); the separately archived Adobe Flash projector EXE is native Windows code and Chromium's PPAPI plugin is native ELF code. Neither native player was launched or transpiled as a working player. For **Rapper Rhythm**, an actual copy of the game ZIP is still needed to learn whether it contains a projector, SWF, or something else.
